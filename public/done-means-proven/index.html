Done Means Proven

How I made my AI coding agent prove its work.

I kept cleaning up after my AI agent. It was fast, but left alone it guessed, duplicated code, and said work was done before it was proven. So I built the process it has to follow, and each part exists because of a problem I ran into on real projects.

The problems, and what I changed

The problem

It made a mess instead of reusing what was there

I already had a components folder. The agent would still create a new folder for a dashboard and write new components inside it, and the project got harder to navigate each time.

Now reusable code is known before anyone writes anything, and unplanned files and duplicates get stopped.

The problem

It guessed

Agents would plan around file structures that didn't exist in my project.

Now the real project gets mapped before any planning. On one test feature, that step flagged a cross-site scripting risk before any code was written, and the fix went straight into the plan.

The problem

Code came before agreement

By the time I saw what had been built, fixing a misunderstanding was already expensive.

Now I approve the plan before any code is written. If that plan changes later, my approval no longer counts.

The problem

"Done" didn't mean it worked

An agent saying the work was finished told me very little, and a fix could quietly break something an earlier check had passed.

Now the final call belongs to something that can't be talked past, and new code voids earlier approvals. In one trial, the checker couldn't start the app, so it reported that it was blocked rather than claiming a pass.

The problem

Every project is different

Some of my projects are fullstack, and others only have a frontend. A fixed process would be wrong for most of them.

Now every job sets its own scope, so a small UI fix doesn't pay for work it doesn't need.

The problem

It burned through tokens

Heavy process on every small change is wasteful, and so is every tool that loads when nobody needs it.

Now small jobs do less, and I measure before I keep something. That's how I learned one of my own optimizations hadn't paid off, and why I removed a tool I'd been maintaining.

What it comes down to

Agree before buildingMisunderstandings are cheapest to fix before code exists.
Prove, don't claimWork counts as done only when there's evidence for the exact code being shipped.
Measure what you keepProcess has a cost, so it has to earn its place.

What measuring changed

3 of 86sessions used the code graph tool I was maintaining, so I removed it.
~61%smaller list of instructions that every session loads up front, estimated from its size.
180+automated checks covering the tooling itself.

Measuring also proved me wrong. I split a large review guide to save tokens, expecting clear savings, but the review cost more in all of my test runs afterward. The sample was small, but it pointed to how much an agent explores as the bigger cost, so I stopped splitting and changed my focus.

Testing found bugs in my own work too. A trial run showed that small UI jobs in some projects would have skipped their end-to-end check, and I fixed that before relying on it.

Where it stands

This is a working personal tool at an early stage, built on Claude Code. An earlier version ran five jobs across three of my projects, each reaching a pull request. I've since rebuilt it, and the current version hasn't yet run a full job on a real feature. That's next, along with better cost data from those runs.

The details stay in a private repository. I'm happy to walk through the design and the decisions behind it in a conversation.
